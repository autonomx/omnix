The shared mental model

How work moves through Omnix

Most features follow the same lifecycle. This makes a generated audio file, an RPG report, a research result, and a coding run observable in the same application surfaces.

01 / INPUTA user action, prompt, file, session command, or scheduled workflow enters a routed workspace.
02 / ROUTEThe shared API boundary selects a domain service, provider, model, capability, or job type.
03 / RUNShort work may run inline; long work receives a durable job/run with stages and resource ownership.
04 / STREAMSSE or WebSocket events carry progress, output, diagnostics, and state transitions to the browser.
05 / STOREStructured truth lives in PostgreSQL; media and documents are indexed as shared assets or reports.
06 / REVIEWThe UI renders the result, while acceptance, evidence, approval, and execution authority stay backend-owned.

The pieces every module shares

Shared concepts

Feature code becomes easier to reason about when it uses the platform vocabulary. The same concepts power both the UI and the backend contracts.

Providers and models

Providers describe connection and capability families. Models describe selectable implementations, location, resource hints, and defaults. Selection is capability-driven and centralized.

Jobs and runs

Long-running work has a durable identity, queue/execution status, semantic stages, progress, logs, cancellation/retry rules, and a resource class such as LLM, TTS, STT, or image GPU.

Assets and artifacts

Generated and ingested files are indexed once, with type, MIME, path, metadata, and ownership. Features link to shared assets instead of hiding outputs in private stores.

Events and realtime

SSE is the default for one-way progress and status. WebSockets are reserved for true bidirectional sessions such as live voice. Feature modules reuse the shared event client.

Settings and diagnostics

Settings expose the supported configuration surface with scope, owner, timing, and restart semantics. Diagnostics show health and failure state without inventing a second source of truth.

Authority and evidence

Domain state, capability grants, acceptance, evidence coverage, review subjects, and recovery decisions are backend-owned. Model output is a proposal or evidence, not authority.

Reasoning with guardrails

Assistant and generalized agents

Chat is the user-facing entry point for assistant tools, coding work, research, and long-running agent workflows. The runtime adds planning, scoped execution, evidence, acceptance, review, and recovery around model reasoning.

Execution lifecycle

request
  ↓
semantic route → normalize objective
  ↓
plan + TaskGraph → review plan
  ↓
issue scoped capability grants
  ↓
execute in an isolated/local workspace
  ↓
validate candidate + collect evidence
  ↓
accept, independently review, recover, or stop

What the runtime protects

  • Coordinator, reviewer, and subagent authority stays explicitly narrowed.
  • Profiles are ceilings, not grants; approval policy cannot expand issued capabilities.
  • Workspace, candidate, task revision, and evidence subject identities must match.
  • Acceptance is deterministic and bound to the candidate under review.
  • Durable PostgreSQL state is authoritative for recovery-sensitive lifecycle decisions.
  • Trading analysis remains research until a deterministic runtime owns execution authority.

Human approval still matters: low-risk reads may be automatic, while writes, execution, network access, credentials, and destructive effects are governed by capability policy and may require confirmation or explicit approval.
System design

Architecture

Omnix is one product with shared infrastructure. Feature modules specialize the experience; they do not fork the provider, job, asset, event, settings, or authority layers.

Frontend boundary

The browser owns layout, route selection, local drafts, filters, panel state, playback controls, and optimistic presentation. It renders backend truth and submits intent through typed contracts.

Gateway boundary

The FastAPI gateway owns authentication/context boundaries, contract validation, capability projection, service orchestration, event delivery, and compatibility handoff.

Domain boundary

Feature services own domain behavior. RPG simulation, trading paper state, provider health, jobs, artifacts, and settings remain authoritative outside the browser.

Persistence boundary

PostgreSQL is the supported structured runtime. Legacy SQLite paths are compatibility/test/import boundaries, not a second production source of truth.

Run it locally

Setup

The core web application needs Python dependencies, npm dependencies, PostgreSQL, the FastAPI gateway, and the Vite web server. TTS, STT, image generation, market data, and Hermes are optional service boundaries.

PowerShell quick start

docker compose -f docker-compose.postgres.yml up -d
$env:OMNIX_DATABASE_URL = 'postgresql://omnix:<password>@127.0.0.1:5432/omnix'

pip install -r requirements.txt
$env:PYTHONPATH = 'src'
python -m app.persistence migrate
python -m app.persistence verify

npm install

# Terminal 1: gateway
python -m uvicorn app.gateway.main:app --host 127.0.0.1 --port 8000

# Terminal 2: web app
npm run web:dev

Open http://localhost:5173/. The Vite server proxies /api and /events to the gateway.

Bash / WSL quick start

docker compose -f docker-compose.postgres.yml up -d
export OMNIX_DATABASE_URL='postgresql://omnix:<password>@127.0.0.1:5432/omnix'

pip install -r requirements.txt
export PYTHONPATH=src
python -m app.persistence migrate
python -m app.persistence verify

npm install
npm run web:dev

Run the gateway in one terminal and the web app in another when using the separate process workflow.

Extend the platform

Development model

Start by identifying the layer that owns the behavior. Then add the smallest coherent change, update focused regression coverage, inspect the complete diff, and validate after the final mutation.

UI

Add a browser workspace

Place feature code under src/apps/web/src/features, register the route centrally, reuse the design system, Query, event client, and typed API client.

API

Add a backend contract

Define the FastAPI/Pydantic boundary, keep resources coherent, regenerate OpenAPI-derived frontend types, and add contract/error tests.

Async

Add long-running work

Use a shared job/run with semantic stages, progress, cancellation/retry behavior, a resource class, logs, events, and asset-backed outputs.

Provider

Add a provider or model

Implement the shared provider layer, advertise capabilities, expose health/readiness, keep credentials out of UI/source, and route by capability.

Data

Change persistence

Add a forward PostgreSQL migration, test clean and upgrade paths, preserve recovery semantics, and run persistence verification.

Governance

Add a tool or setting

Declare scope, risk, effect, approval, credential/network needs, timing, writability, audit behavior, and a real runtime consumer.

Keep the system understandable

Operations and diagnostics

When something fails, identify the unavailable layer before changing configuration. The diagnostics workspace, shared Jobs view, provider status, event state, and database verification are designed to make that boundary visible.

Fast triage order

  1. Check the browser URL and Vite process.
  2. Request /api/health from the gateway.
  3. Verify PostgreSQL connectivity and migrations.
  4. Inspect provider/model status and capability readiness.
  5. Check the job, resource lock, logs, and event stream.
  6. Only then tune feature-specific inputs or model settings.

Safe operating rules

  • Keep provider keys in the protected secret flow or environment, never in source or general settings.
  • Treat blobs and generated assets as recoverable outputs with ownership and retention policy.
  • Load heavyweight image models explicitly; service health does not imply model residency.
  • Keep Hermes optional and proposal-scoped until its reachability and policy boundary are verified.
  • Keep trading AI in research/paper mode unless deterministic execution authority is explicitly configured.

Common questions

FAQ

Is Omnix local-only?

It is local-first and supports local services such as LM Studio, llama.cpp, TTS/STT/image workers, and PostgreSQL. The provider abstractions also support cloud-compatible or remote providers.

Does the model control tools or external effects?

No. The model can propose or request actions from capabilities that Omnix has issued. The registry, broker, scope, approval policy, credentials, confirmation rules, and audit boundary remain deterministic Omnix code.

Can I use SQLite for production?

PostgreSQL is the supported structured runtime. Legacy SQLite modes exist only for compatibility, tests, or controlled imports where explicitly enabled.

Why is a service healthy but a feature unavailable?

Service process health and feature readiness are separate. A provider may be reachable while a model is not downloaded, not loaded, missing a capability, blocked by policy, or waiting for a worker/resource lock.

Where should new browser behavior go?

Use src/apps/web and the shared gateway/app infrastructure. The classic src/templates/src/static UI is a compatibility boundary and should not receive new browser features.

How do I enable Hermes safely?

Follow HERMES_SIDECAR_SETUP.html, verify the sidecar endpoint, keep HERMES_ENABLED=false until reachability is confirmed, and remember that Omnix retains capability and application-state authority.
