# Enterprise roadmap implementation decisions

Source: [roadmap](../ENTERPRISE_ARCHITECTURE_ROADMAP_2026-09-27.md).

| 2026-10-03 | WP-11.1 | The gateway image's < 500 MB target is measured as the compressed (pushed) size: 310 MB. Unpacked it is 916 MB, half of it Debian's ffmpeg and its codec libraries, kept rather than a static ffmpeg build. | Audiobook export runs ffmpeg (AAC, MP3, FLAC, cover art) in the gateway and job worker. A static build is 135 MB per binary and hides its bundled libraries from the vulnerability scanner, while Debian's packages get security updates that trivy can see. The venv itself is 308 MB (onnxruntime, pandas, numpy). |
| 2026-10-03 | WP-11.1 | Image scans fail on critical vulnerabilities that have a fix (`trivy --severity CRITICAL --ignore-unfixed`). The upstream `nginx-unprivileged` tags lagged fixed OpenSSL and Nginx packages; upgrading at build time closed them. Pinning digests would freeze those fixes out. |
| 2026-10-03 | WP-11.1 | The gateway image runs `scripts/run_omnix_gateway.py`, which serves `app.production:app`, instead of calling uvicorn directly. | The runner initializes the service credential and establishes PostgreSQL authority before serving; the Compose and multihost deployments already use it. |
| 2026-10-03 | WP-11.1 | GPU images install from new `requirements/{tts,stt,image}.linux.lock.txt`, compiled with pip-tools in a Linux container and seeded from the Windows locks, so shared pins are identical. | The existing GPU locks were compiled on Windows and could not install on Linux: pip-tools writes only the current platform's dependencies, and Torch and `huggingface-hub` need Linux-only packages (`nvidia-*`, `triton`, `hf-xet`). |
| 2026-10-03 | WP-11.1 | Model weights are fetched by `python -m app.models download` from `src/app/models/catalog.json` (a pinned commit per repository and the SHA-256 of every file a service reads) into the Hugging Face cache on a volume; the downloader points the cache's `main` ref at the pinned commit and the services run with `HF_HUB_OFFLINE=1`. | The services load models by repository id (diffusers, NeMo, Qwen3-TTS). | 2026-10-03 | WP-11.2 | The `storage` profile runs SeaweedFS, not MinIO. | SeaweedFS is the S3 backend the blob-store contract and the multihost test already run against (WP-5.8, WP-6.8), and MinIO no longer publishes community images. |
| 2026-10-03 | WP-11.2 | Grafana in the `observability` profile serves its provisioned dashboards anonymously and read-only, with the login form and basic auth off, instead of requiring an admin password. | Compose interpolates every service, including those of inactive profiles, so a required Grafana password would also block the core stack. Sharing the names keeps the existing local database in use; the overrides let a test stack run without touching it. |
| 2026-10-03 | WP-11.3 | The ingress no longer honours `X-Omnix-Gateway-Affinity` from clients (policy `external_worker_affinity: false`) and strips it before proxying; the Vite development proxy still honours it. | Only the routing policy should decide what reaches the worker. No client or script sends the header through the ingress. |

Pixi otherwise compiles shader code with `new Function`; its eval-free module removes the need for `'unsafe-eval'`. Chromium loaded the built app under the policy with no violation. |
| 2026-10-03 | WP-11.1 | Two production defects found by the container work were fixed in place: Pillow joins the gateway lock (the audiobook service and image output normalization import it, and production installs lacked it), and `GET /api/settings` returns each setting's revision, which the web provider form and the multihost driver now send back (`POST /api/settings` refuses an existing setting without its revision, so neither could save). | An import sweep of every `app` module in the gateway image found the missing package; the multihost topology test on the new image found the settings contract gap. |
| 2026-10-02 | WP-10.4 | OpenTelemetry ships as `requirements/tracing.lock.txt` (the gateway lock plus OTel) and `dev.lock.txt` layers on it; the Dockerfile takes `OMNIX_LOCK=tracing`. A durable job starts its own trace in the worker rather than continuing the submitting request's trace; `request_id` (the job's correlation id) joins them. Live speech stages are recorded as finished spans from the turn's timestamps. The TTS, STT and image services are not instrumented. | The optional extra keeps the base gateway install unchanged and the tests able to run with an in-memory exporter. Carrying a `traceparent` through `omnix_jobs` would need a migration for a link the correlation id already provides. The live speech pipeline is event-driven (it marks times), so there is no block to wrap. The model services run in their own locked environments; their requests from the gateway already appear as httpx client spans. |
| 2026-10-02 | WP-8.5 | Proceed with Memory v2, the VoiceMem-derived dual-brain memory (owner decision), in three steps: fix its lexical search, add VoiceMem's embedding retrieval (multilingual-e5-small), then rerun the v1/v2 benchmark before the authority switch. Embeddings are stored in PostgreSQL rows and compared in Python, not with pgvector. | The benchmark showed v2's structure without VoiceMem's retrieval losing to v1. pgvector is not in the `postgres:17-alpine` image the installation runs, and changing the operator's database container is out of bounds; a few thousand 384-dimension vectors per space compare in milliseconds with numpy. |
| 2026-10-02 | WP-8.2 | Agent run token and cost defaults are a settings option (owner decision): `agentRuns.defaultMaxOutputTokens`, `agentRuns.defaultMaxCostUsd` and per-provider prices (`agentRuns.providerPrices`, USD per million input and output tokens), all unset by default. | Runs started without their own limits take the defaults; explicit limits win. A cost limit was only enforceable on local providers (anything else failed as unmeterable); a configured price now makes a paid provider meterable, and each call is charged at that price and stopped with `budget_cost_exhausted` past the limit. Unset defaults keep today's behaviour. The web merge kept only known keys, which silently dropped every free-form map (provider prices, but also storyteller pronunciations and RPG campaign defaults); an empty default now means a free-form map. |
| 2026-10-02 | WP-8.2 | Implement `gmail.send_email` (owner decision): the personal-assistant profile advertises it and the intent router selects it for "send", but the adapter had no send, so every send request failed. | It sends through Gmail's `messages.send` (or `drafts.send` for an existing draft) with the `gmail.modify` scope the connection already requests. The capability stays high risk with confirmation required, so it runs only through an approved proposal; recipients are validated (addresses with a domain, at most 20) and header injection is refused by `EmailMessage`. |
| 2026-10-02 | WP-11.6 | Keep the voice-clone sample WAVs in the repository (owner decision). | The owner reviewed them and chose to keep them; no consent manifest is required by this decision. |
| 2026-10-02 | WP-10.4, WP-11.1 | Add OpenTelemetry as an optional dependency, and build container images locally with Docker (owner approval). | Requested in the roadmap; both need the owner's approval because they add dependencies and large builds. |
| 2026-10-02 | WP-10.6 | Validate the alert rules and dashboard with a pytest schema check that also ties every metric they use to the catalog in `METRICS.md`, not with `promtool`. | `promtool` is not installed locally or in the CI image; the roadmap allows a YAML schema check instead. Tying expressions to the catalog catches the failure that matters most here: an alert on a metric name that does not exist never fires. |
| 2026-10-02 | WP-10.5 | The silent broad excepts keep their behaviour and log at debug with the traceback, rather than being narrowed or raised to warnings one by one. | They are best-effort paths (cleanup, optional enrichment, provider fallbacks, process control, RPG template fallbacks), many in loops; a warning would flood logs with expected failures, and narrowing each type needs the failure modes of 104 modules. Debug logging makes every suppression traceable on demand at no cost when disabled (`isEnabledFor` first). Sites that turn out to matter can be promoted, with a metric, as they come up. |
| 2026-10-02 | WP-10.5 | Step 2 starts with the details that echo a broad `except Exception` into a 5xx; 4xx details built from a `ValueError` or a domain error's text stay. | Those 5xx details are the leak: a provider or driver error carries URLs, keys, file paths and SQL. Validation and domain errors are raised by Omnix code with messages written for the caller (about 180 sites); rewriting them as codes changes what the UI shows without removing a leak, so they move route by route with the UI. |
| 2026-10-02 | WP-10.5 | The problem-details envelope keeps each route's existing `detail` value (a string, an object such as `{"error": "rate_limited", "limit": "login"}`, or the validation error list) and adds `code` beside it, rather than replacing `detail` with an RFC 9457 string now. The handlers live in `app/errors.py`. | The web client, scripts and about 50 tests read `detail`; changing its type in the same step as the envelope would break them all at once. `code` gives machines a stable field today (taken from a code-like detail, its `error`/`code` field, or the status). Step 2 turns details into codes plus safe messages route by route. `app/errors.py` already loads at boot, so the envelope adds no boot module. |
| 2026-10-02 | WP-10.3 | Database time is measured as connection hold time per statement class (`omnix_db_connection_hold_seconds`), not statement duration per repository method. | Every transaction and unit of work checks a connection out of `PostgresDatabase.connection()`, so one timer there covers them all; the statement class (request, job, maintenance) is already bound by the callers. Per-method timing would need a wrapper on each repository method (hundreds) or statement-level hooks on every query. Hold time also shows the cost that matters for pool sizing: work that keeps a connection while doing something else. |
| 2026-10-02 | WP-10.3 | Mark WP-10.3 done with four catalog items left as follow-ups: per-repository-method statement duration (sampled), a pool wait-time histogram, live voice call timings and active calls, and the agent-run and Chat streams' SSE counters and outbox publish rate. | The acceptance is met: the endpoint test asserts the catalog names, and every label is bounded (route templates, status classes, registered job types, client names, fixed reason codes). Each follow-up needs its own instrumentation point (per-method wrappers, a checkout wrapper, the live voice transport, each stream route), listed in `docs/operations/METRICS.md` under Planned. |
| 2026-10-02 | WP-10.3 | Provider metrics are recorded per attempt in `PooledHttpClient`, labelled by client name, through an attempt observer the gateway installs (`app.runtime` does not import `app.observability`); circuit refusals are an outcome rather than a circuit-state gauge; metric recording is a no-op where `prometheus_client` is not installed. | Every provider and model-service call already passes through the pooled client, so one place covers them all without touching each provider. A direct import would close a package cycle (observability already imports `app.runtime.paths`). A state gauge would need a registry of every live client; refusals counted per client show an open circuit as directly. The TTS and STT service environments do not lock `prometheus_client`, and a missing metrics library must not break them. |
| 2026-10-02 | WP-10.3 | Pool wait is exposed as cumulative counters (requests and total wait seconds) from psycopg_pool's statistics, not as the wait-time histogram the roadmap lists. | psycopg_pool records only a running total of wait milliseconds; a histogram would need a wrapper around every connection checkout, which sits on every request's path. The two counters give the mean wait per interval; a histogram can follow if tail waits matter. |
| 2026-10-02 | WP-10.3 | Job queue metrics are gauges read from PostgreSQL when `/metrics` is scraped, over a new partial index of active jobs (migration 0116); every gateway process reports the same workspace-wide values. | Queue depth and age are database facts, not process facts; counting them in-process would miss jobs submitted by other processes. The existing diagnostics query grouped every job ever run (a scan of the table); the partial index keeps the scrape to the active jobs (14 ms with 25,000 queued at benchmark volume). Claim, retry and execution-duration counters belong to the worker process, which does not serve metrics yet. |
| 2026-10-02 | WP-10.3 | Serve `/metrics` on the main app behind `admin:metrics`, not on a private `OMNIX_METRICS_PORT` listener. | The roadmap allows either. The main app already has authentication, the permission table and the listener policy; a second listener would need its own bind, host and port-conflict handling in every launcher. With sign-in off the local owner can scrape, as it can read `/api/diagnostics`. |
| 2026-10-02 | WP-10.3 | Build the `prometheus_client` registry on the first recorded request, not at import. | Importing `prometheus_client` loads 28 modules (its package imports the exposition servers); composing the gateway records nothing, so the boot ratchet stays where it is and the first request pays the import once. The middleware sits inside sign-in, so routes are resolved and labels are route templates. |
| 2026-10-02 | WP-10.2 | Request ids go to Omnix's own model services only, not to third-party LLM providers; the web client shows the id in API error messages rather than through a separate error-report endpoint. | A third-party provider cannot log under our id and gains a cross-request identifier; the gateway already logs each provider call under the request id, which is the correlation the acceptance test asks for. No client error-report pipeline exists, and the message is what a user copies into a report; test doubles without the header keep the old message. |
| 2026-10-02 | WP-10.2 | Model services keep a valid inbound `X-Request-ID` before authenticating the call, and the gateway forwards its bound id with the service credential. | The id is correlation only and grants nothing; it is format-checked like the gateway's, so an unauthenticated caller can at most label its own rejected request. Forwarding it in `service_headers()` covers every TTS, STT, Qwen and image call in one place, including calls made by workers under a job's id. |
| 2026-10-02 | WP-10.2 | A job stores the submitting request's id in a new `omnix_jobs.correlation_id` column (expand migration 0115, nullable, at most 128 characters), and workers bind it as the log field `request_id` rather than a separate field. | One key finds every line of a submission, from the request through the job and its provider calls. The store reads the id from the log context, so routes need no change and a job submitted inside a running job inherits it. A column, not job metadata, so it can be indexed and queried later. |
| 2026-10-02 | WP-10.2 | Generated request ids are `uuid4().hex`; update the `chat-live-sse-turn` golden for the `job` event's new `correlation_id` field. | The characterization harness normalizes UUID-shaped values, so the golden only gains the field (the job id's placeholder renumbers because the new key sorts first); every other event and the transcript-store calls are unchanged. 32 hex characters fit the inbound id format. |

| 2026-10-02 | WP-8.5 | Chat provider calls use a fixed pool of twice the dispatcher's worker count; cross-process cancellation is read from the job store once a second. | The four dispatcher workers already bound concurrent turns, but an interrupted provider call keeps running until the provider returns, so repeated interruptions used to accumulate threads. In-process cancellation wakes the worker through the job's `CancellationToken`; only a cancel made on another gateway process needs the store, and one read a second (instead of ten) bounds that delay at about one second. |

| 2026-10-03 | WP-8.5 | The shadow runner is the authoritative feed into Memory v2 before cutover: after each sync it advances a space's authoritative event watermark to its observation watermark. | 2026-10-03 | WP-8.5 | Shadow quality is scored by evidence identity, not text similarity: each probe asks v2 for one v1 record by its own words under that record's scope plus the profile's global scope; recall counts probes whose record came back (threshold 0.95), precision counts returned memories backed only by active, visible v1 records (threshold 1.0). | Real data has no question set. | 2026-10-03 | WP-8.5 | Cutover safety: v1 record writes share-lock the authority row inside their own transaction and refuse once v2 is authoritative; activation re-checks under that lock that v1 has not changed since the shadow run and that every imported space has a receipt, and may run with no receipts only when v1 holds no memory; rollback refuses once anything was written or governed under v2 in any space. | 2026-10-08 | Runner WP | Gap pullback configurations gain `execution_owner`: `monitor` (default), `runner_shadow` or `runner`. `runner` moves the whole pass to the runner and the monitor skips the configuration. `runner_shadow` keeps the monitor as owner; the runner runs the same pass with strategy-event writes discarded, every other strategy write and every paper write refused, and protections, the intraday LLM and diagnostics left to the owner, then records its proposals as `runner_parity_proposal` events while the monitor records its own as `monitor_parity_proposal`; `runner_parity_report` compares them by trade attempt. Accepted by the auto-paper replay: with `runner` as owner the runner places the identical order, protection and strategy events (run ids aside), and with `runner_shadow` the trade is unchanged and parity holds. |

## TradingView parity roadmap

Source: [TradingView parity roadmap](../trading/TRADINGVIEW_PARITY_ROADMAP_2026-10-08.md). Ids are `TVP-n.n` work packages and `D-n` decisions from its §7.

| Date | Id | Decision | Reason |
|---|---|---|---|
| 2026-10-08 | D-1 | Omnix supports a TradingView-compatible subset of Pine Script so users can paste existing scripts. The product is named "Omnix Scripts" and described as Pine-compatible. Scripts produce indicators, alerts and backtests; strategy scripts can drive paper accounts at most. | Owner decision: existing scripts are the main reason traders stay on TradingView. "Pine Script" is TradingView's trademark, and AGENTS.md keeps order authority with deterministic strategies. |
| 2026-10-08 | D-2 | Paper trading works like TradingView's: short any instrument, leverage per asset class, separate long and short margin %, margin calls that force-close positions, % or fixed commission, no borrow fees. The account form turns shorting on by default; the model and database default stay off, so strategy-created and existing accounts are unchanged, and the default margin of 100% keeps current behaviour. | Owner decision for parity. Strategies create paper accounts through the same model, so a model-level default would change strategy paper behaviour as a side effect. |
| 2026-10-08 | TVP-7.1 | Paper orders gain `stop_limit`, `trailing_stop` (by amount or %), and time in force `gtc` (default), `day` and `gtd`; migration `0140_trading_paper_order_types`. A DAY order's expiry is fixed when it is placed: US equities (`equity:`) expire at the next regular-session close after placement (`us_equity_calendar`, early closes included), so an order placed after the close or on a closed day lasts until the next session's close; every other market trades around the clock and its DAY ends at midnight UTC. Expired orders get the new status `expired` (reason `time_in_force_expired`) and release their holds; the paper monitor expires them on the server clock even when the instrument has no data, and no observation at or after the expiry can fill them. | Defaults keep every existing and strategy-owned order GTC with no trailing. UTC midnight is a fixed, timezone-free "day" for 24/7 markets. A separate status keeps expiries apart from user cancels in history and analytics. |
| 2026-10-08 | TVP-7.1 | Fill semantics stay pessimistic. A stop-limit order that reaches its stop fills in that observation only at the gap-through price (the worse of stop and current price) and only within the limit; otherwise it rests as a limit order, and a bar's range counts only if the bar started strictly after the trigger. A trailing stop is armed by its first usable observation, its fill check uses the stop from before the observation, and only then does the observation's causal high (a buy's low) move the water mark. Trigger time, water mark, current stop and when the stop last moved (`trail_moved_at`) are persisted on the order, so a restart resumes the same trail. A bar's range can trigger a moved stop (a trailing order, or any bracket leg whose stop trailed or was edited) only when the bar started strictly after the move; otherwise only the current price counts, because the monitor re-reads the same forming bar and its low may predate the move. The move is stamped with the later of the quote time and the bar's start (a quote can be seconds older than the bar it arrives with); saving an active leg with a new stop, or making a leg active, stamps the database clock (`clock_timestamp()`). Trailing stops and trailing-stop fills round to the instrument's catalog tick against the trader (a sell's stop and fill down, a buy's up); an instrument not in the catalog keeps unrounded prices, and other order types are priced as before. A stop or stop-limit already through the market is accepted and triggers on the next price, as plain stops always did; the ticket warns instead of refusing. | A bar does not say whether its extreme came before or after the trigger, so the fill must not assume the favourable order. Rounding away from the market keeps the trail at least as wide as asked. |
| 2026-10-08 | TVP-7.1 | Bracket legs: the stop-loss leg can trail (`trail_amount`/`trail_percent` on the protection; risk entries send `trailing_stop_loss`, which trails by the entry-to-stop distance). The monitor raises `stop_loss` behind the persisted water mark, never loosening it, without bumping the protection revision. Stop-limit legs are not offered: a protective exit that can leave the position open on a gap defeats the bracket. Legs are GTC for the life of the position; time in force applies to the entry, and an entry that expires unfilled cancels its pending bracket in the same transaction. Editing an active trailing leg without changing its trail (the chart sends the trail back with every level move) keeps the water mark; a changed stop counts as a move of the trailed stop, and one looser than the trail implies is tightened back on the next update. Changing the trail or re-arming starts afresh. Replay tickets keep market, limit and stop with GTC (replay snapshots carry no trigger state or session clock); the server refuses the new types there (TVP-8 follow-up). DAY for futures and forex uses midnight UTC for now; venue session closes (e.g. CME 17:00 ET) are a follow-up. | The protection model already exits by market order on a trigger, so a trailing stop is a moving trigger and fits without a redesign. TradingView offers trailing on the stop-loss leg the same way. |
