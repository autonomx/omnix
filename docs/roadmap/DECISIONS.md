# Enterprise roadmap implementation decisions

Source: [roadmap](../ENTERPRISE_ARCHITECTURE_ROADMAP_2026-09-27.md).

| Date | WP | Decision | Reason |
|---|---|---|---|
| 2026-10-01 | WP-5.2 | Retention runs under a `retention` system scope (by age and state), not per workspace. | Eligibility never depends on the tenant, and one pass over the index is cheaper than one per workspace; row-level security still confines every other path. |
| 2026-10-01 | WP-5.2 | Trading strategy event retention ships disabled (180 days configured). | Strategy qualification reads long event windows; deleting history could change qualification results, so enabling it is an operator decision. |
| 2026-10-01 | WP-5.2 | RPG snapshot retention ("last 20 per campaign plus every 100th turn") is not implemented. | RPG is being retired; narration events already have a policy. |
| 2026-10-01 | WP-5.2 | `omnix_capacity_policy` stays advisory: it bounds cleanup batch size and reports capacity, admission is not refused on disk thresholds. | Refusing work at admission needs a disk measurement each replica can trust (planned with WP-10 telemetry); a wrong refusal would stop all jobs. |
| 2026-10-01 | WP-5.2 | CI runs one retention pass before the runtime probe measures `retention_policies_executed`. | The probe is read-only by design; the measurement then shows that one pass of the real command executes every enabled policy. |
| 2026-10-01 | WP-5.2 | No partitioning yet. | No table is near 20M rows, and batched deletes stay small; revisit with the soak benchmark. |
| 2026-10-01 | WP-4.2 | Scheduled tasks opt into `per_workspace`: the scheduler keeps one advisory lock per task, and each run iterates the active workspaces, pushing that workspace's system tenant. Trading tasks stay single-workspace. | Recovery tasks (lease release, chat recovery) must reach every workspace once multi-workspace sign-in is on; one lock per task keeps exactly-one scheduling (WP-6.3). Trading has one account per installation. Process-executor tasks cannot carry a tenant and are refused. |
| 2026-10-01 | WP-4.9 | Assistant-tool credentials and OAuth clients are one secret per workspace and kind (`assistant-tools/<workspace>/credentials`); the plaintext file branch and the document-service stubs are removed. | One read-modify-write per change keeps the store simple and naturally tenant-scoped; the old non-PostgreSQL branch was the only plaintext writer. |
| 2026-10-01 | WP-4.9 | `auto` falls back to the read-only environment store when neither DPAPI nor keyring is available; saving then fails closed (`SecretStoreUnavailable`). `keyring` stays an optional extra. | No plaintext backend, as the roadmap requires; containers usually receive secrets as environment variables. |
| 2026-10-01 | WP-4.9 | Provider API keys stay in the existing DPAPI provider store (`provider_secret_store.py`). | It already meets the requirement (OS-protected, environment authoritative); moving it is a separate migration of existing user data. |
| 2026-10-01 | WP-4.9 | Tests install an in-memory store through an autouse fixture. | Tests must never write the developer's real DPAPI file or keychain. |
| 2026-10-01 | WP-4.10 | Private networks are allowed for outbound endpoints while sign-in is off; with sign-in on they need `OMNIX_ALLOWED_PRIVATE_NETWORKS`. Link-local and metadata addresses are always refused. | The roadmap's default (no private networks) would break a local install whose model servers live on the LAN; the single local user configures their own network. Cloud metadata is the critical SSRF target and stays blocked everywhere. |
| 2026-10-01 | WP-4.10 | Connect-time checks resolve the host and refuse if any address is blocked; a name that does not resolve is left to the request's own error. The request then resolves again (a short TOCTOU window remains). | Pinning the connection to the checked address needs a custom transport in each provider client; the check closes the stored-hostname rebinding case at low cost. |
| 2026-10-01 | WP-4.10 | API docs are replaced by permission-guarded routes (`admin:docs` outside development); the exported OpenAPI is unchanged. | FastAPI's built-in docs routes bypass the dependency system, so they could not carry the guard. |
| 2026-10-01 | WP-4.10 | Gateway CSP: `default-src 'none'` for non-HTML responses; HTML (Swagger UI, previews) only forbids framing, base and object unless the route sets its own policy. | The web app is served by Vite or the ingress with its own policy (WP-11.3); the gateway's own pages need their scripts. |
| 2026-10-01 | WP-4.10 | Not yet done: hiding `storage_path` from asset responses (about 40 web call sites read it, some as voice paths) and the raw-exception envelope (WP-10.5). | Removing the field needs the web clients to move to file names and content URLs first; doing it here would break voice flows. |
| 2026-10-01 | WP-4.8 | Writes are audited by the permission guards: the permission a route requires maps to an audit action (`PERMISSION_AUDIT_ACTIONS`), recorded after the handler with success, failure or denied. Approvals, capability execution and agent run start/stop are recorded where they happen, with real target ids. | It covers settings, trading control, paper orders, feature toggles, tool connection secrets and administration without editing every handler, and a new route under an audited permission is covered automatically. The guards became async generators, which also removes their threadpool hop. |
| 2026-10-01 | WP-4.8 | `omnix_audit_events` is append-only through a trigger (UPDATE/DELETE raise, except foreign-key actions and an explicit `omnix.audit_maintenance` session for retention); the runtime role additionally loses UPDATE/DELETE. | A trigger binds every role, including the superuser that local installs use; revoking grants alone would only protect separated deployments. |
| 2026-10-01 | WP-4.8 | `record()` never raises: a failed audit write is logged. Without an installed sink (no database), recording is a no-op. | The audited action has already happened or been refused; failing the request afterwards would misreport it. Persistence startup always installs the PostgreSQL sink. |
| 2026-10-01 | WP-4.8 | Provider API keys are audited as `settings.update` (they are settings writes); `secret.*` covers tool connection credentials until the secret store (WP-4.9) owns secrets. | Provider keys are saved through the settings routes today. |
| 2026-10-01 | WP-4.6 | Run tokens are checked in the authentication middleware for the agent routes in every auth mode; the token's workspace becomes the request tenant with an `agent_run` role (`agent:read`, `agent:run`, never approve). | With sign-in on, Pi's loopback calls used to run as the local owner. Binding the tenant before routing lets row-level security and the permission guard apply to agent calls like any other request. |
| 2026-10-01 | WP-4.6 | The payload adds `workspace_id` and `owner` (the agent service's worker id) to the roadmap's fields, and drops `attempt`. A route dependency rejects tokens whose run has finished, whose capability digest changed or whose owner no longer holds the run. | A takeover by another owner is the attempt boundary the runtime actually has. The workspace lets agent runs outside the local workspace reach their own data. |
| 2026-10-01 | WP-4.6 | Signing key: `OMNIX_RUN_TOKEN_KEY`, else HMAC-derived from the launcher's `OMNIX_SERVICE_TOKEN`, else a random per-process key; `gateway_cluster.py` generates a shared key for its replicas. | The secret store (WP-4.9) does not exist yet. Every multi-process topology already has a service token or now gets a cluster key; a hand-started single process works with its own key. |
| 2026-10-01 | WP-4.6 | The model provider sends the token as its OpenAI API key (`Authorization: Bearer`), and the gateway accepts `Bearer` as well as `OmnixRun` on agent routes. Renewal re-registers the provider. | Pi's OpenAI client always sends `Authorization: Bearer <apiKey>`, and a second Authorization header would be ambiguous. |
| 2026-10-01 | WP-4.6 | Agent routes stay on the main listener; the loopback-only exemption is removed because the token is the authentication. A separate agent listener (`OMNIX_AGENT_LISTENER_PORT`) is not added. | It was optional in the roadmap. Containers and multi-host workers reach the broker over the network with their token. |
| 2026-10-01 | WP-4.5 | `app.capabilities.executor` is a kernel facade: callers build a `CapabilityGrant` and call `execute_capability`; the assistant-tools feature installs the runtime (review, fail-closed adapter registry, ledger) through a runtime hook. | Callers in chat, agent runtime and assist-core depend on the kernel instead of importing assistant-tools internals. With assistant-tools disabled, execution fails closed (`CapabilityRuntimeUnavailable`). Tests get the same runtime from an autouse fixture. |
| 2026-10-01 | WP-4.5 | Approvals carry the approving principal without schema changes: agent approve commands stamp `issued_by` server-side and the owner copies it into the approval's `resolution_payload.decided_by`; workflow steps keep `approved_by` in the step result until they run; task-graph approval nodes record it in their output. | The JSONB columns already exist and the public response models are unchanged (no API contract churn). Decisions recorded before this change execute as `unrecorded:before-principal-binding`, so in-flight runs are not stranded at upgrade. |
| 2026-10-01 | WP-4.5 | The self-approval ceiling (`OMNIX_APPROVAL_SELF_ALLOWED_MAX_RISK`) defaults to `high` while sign-in is off and `low` when it is on. | With sign-in off there is one local user, who must be able to approve their own requests. The owner keeps sign-in off for now. |
| 2026-10-01 | WP-4.5 | The broker charges the tool budget once per claimed capability execution, and the Pi guard no longer charges `omnix_capability`. | A run that bypasses the guard can no longer make unmetered capability calls. Calls that only return "approval required" are not charged, and replays of a completed call are free. |
| 2026-10-01 | WP-4.5 | A chat "confirm" approves only when the confirming user has `tools:approve`; otherwise the grant stays unapproved and the tool policy refuses the call. | A chat message is an approval decision and follows the same rule as the approval API. |
| 2026-10-01 | WP-4.4 | Set `omnix.workspace_id` and `omnix.system` per pooled connection at checkout (session level, cached per connection), from the current tenant. | Every database path goes through `PostgresDatabase.connection()`, including units of work and raw connections. Setting the scope at checkout needs no change at 126 transaction sites, and costs one round trip only when a connection changes tenant. A unit of work runs entirely as the tenant that opened it. |
| 2026-10-01 | WP-4.4 | Cross-workspace work uses a named system scope (`SYSTEM_OPERATIONS`: identity provisioning, membership resolution, workspace listing, sign-in lookups, migrations, operator CLI) instead of a `SECURITY DEFINER` workspace-listing function. | Sign-in and membership resolution run before the workspace is known. Workers already iterate workspaces with `push_tenant`. A short, reviewed allowlist covers the remaining cases without a second database role. Like the policies, the setting guards against a forgotten filter, not against SQL injection. |
| 2026-10-01 | WP-4.4 | Child tables without `workspace_id` (asset/character versions, job attempts, memory snapshot items, outbox consumer inbox) follow their parent row via an `EXISTS` policy. System audit events (`workspace_id` NULL) can be written by anyone and read only in system scope. | Keeps every tenant table covered (`rls_coverage` 100%) without adding denormalised columns. |
| 2026-10-01 | WP-4.4 | `0106_row_level_security` is a contract migration. | Older code does not set the workspace and would read no rows under a non-superuser role, so it must be applied after every process is upgraded. |
| 2026-10-01 | WP-4.4 | CI's main PostgreSQL job runs the application and the marked PostgreSQL/multiprocess suites as a restricted `omnix_app` role (DML only, no `BYPASSRLS`). The superuser migrates and runs the PostgreSQL architecture gate (migration contracts, fixtures that create tables). | Proves the application works under row-level security. Superuser installs (the local default) bypass the policies, so the default path is unchanged. Converting the 45 DDL- and fixture-bound persistence cases to the runtime role is follow-up work. |
| 2026-10-01 | WP-4.4 | `persistence backup`/`restore` use the migration role. | Under row-level security a runtime role cannot dump every workspace, and a restore recreates the schema. |
| 2026-10-01 | WP-4.3 | Attach a permission guard to every router at composition (feature default read/write; kernel path table), with per-route permissions in one central table plus `openapi_extra=requires(...)`. | Covers ~630 routes without editing every decorator, and keeps the exceptions reviewable in one file. Kernel routes without a mapping fail closed. A runtime test proves that a caller without permissions is refused on every non-public route, including WebSockets. |
| 2026-10-01 | WP-4.3 | Trading writes default to `trading:control` (admin); member actions such as paper orders are opted in per route. | Strict by default: a new trading route is admin-only until someone grants it explicitly. |
| 2026-10-01 | WP-4.3 | Agent and task-graph approvals are checked from the command payload (`approve`/`reject` need `agent:approve`, `steer` needs `agent:steer`). | They share one `/commands` route with run-level commands, so the route-level default (`agent:run`) cannot distinguish them. |
| 2026-10-01 | WP-4.3 | The `routes_without_permission` metric counts routes of composed packages as authorized (629 → 47); the remaining 47 are sidecar apps protected by service tokens or loopback. | Guards are attached at composition and the metric is static; the runtime enumeration test is the authoritative check. |
| 2026-10-01 | WP-1.4 | Re-ensure the local identity before each `postgres`-marked test. | Persistence tests truncate shared tables (cascading to workspaces). Under xdist another PostgreSQL test could run in that window and fail with a foreign-key violation (nightly full suite). |
| 2026-10-01 | WP-4.2 | Bind the request tenant in ASGI middleware (inside authentication) rather than a per-router `Depends(require_principal)`. | Middleware covers every HTTP and WebSocket route, including routes outside feature routers, and keeps the context for streamed responses. `require_principal` remains available as a dependency for handlers that need the principal. |
| 2026-10-01 | WP-4.2 | Replace construction-time tenant capture with a `RequestTenant` descriptor on 32 services. | Process-wide services captured the startup tenant, so every request ran as the local workspace. An injected context still wins; otherwise each read follows the request (or job) tenant. Single-workspace behaviour is unchanged. |
| 2026-10-01 | WP-4.2 | Job workers iterate active workspaces (round-robin) using a per-workspace system context (creator user, `system` role). | Claim queries are workspace-scoped, so jobs submitted in another workspace would never run. Iterating per workspace also matches the per-workspace transactions WP-4.4 (row-level security) needs. |
| 2026-10-01 | WP-6.8 | Set uvicorn's keep-alive (75 s) above Nginx's upstream keep-alive (60 s). | With uvicorn closing idle connections first (5 s default), Nginx can reuse a dying pooled connection; with `proxy_next_upstream off` that becomes a 502. This also affects production Nginx deployments. |
| 2026-10-01 | WP-6.8 | Use SeaweedFS for S3 in the topology, CPU fake model services, and a story (text) asset for the cross-host asset check. | MinIO images now need authentication. The gateway image does not include Pillow, so text assets are the portable cross-host content check; images follow the same blob path. |
| 2026-10-01 | WP-6.8 | Generate the topology's Nginx config from the production routing policy (`render_gateway_ingress.py`, now parameterised by upstream addresses). | The test then exercises the same routing maps as production, not a hand-written copy. `--check` covers both files. |
| 2026-10-01 | WP-6.8 | Trim the Docker build context in `.dockerignore`: dot directories, local scratch, operator runtime data and the web app. | The context had reached 17 GB of local data and caches, and unreadable cache folders broke the build. The gateway image needs none of it; CI builds from a clean checkout. |
| 2026-10-01 | WP-6.8 | Assistant-memory settings fall back to their registered defaults when the feature is disabled. | With `OMNIX_FEATURES` excluding assistant-memory, chat session creation crashed while reading transcript-retention policy through the memory contract. The mock-compute soak and the topology found it. |
| 2026-10-01 | WP-6.8 | Story saves stage the manuscript in a temporary directory unless the store is the legacy file manifest. | Under PostgreSQL authority the save failed with a 500 (`manifest_path` exists only on the legacy store); the asset store copies the file into blob storage on upsert. |
| 2026-10-01 | WP-5.8 | Raise the `routes_without_permission` ratchet by one (628 → 629) for `GET /api/assets/{asset_id}/audio`. | The route replaces base64 audio in job rows. No permission system exists before WP-4.3, which assigns permissions to every route and takes this metric to 0. A fake dependency would only hide the gap. |
| 2026-10-01 | WP-5.8 | Implement the S3 BlobStore over `httpx` with AWS Signature Version 4 instead of adding `boto3`. | `httpx` is already hash-locked. Adding `boto3`/`botocore` would mean recompiling several platform-sensitive locks. The signer reproduces AWS's published GET, PUT and presigned-URL signatures exactly (tests), and an authenticating server rejects wrong keys. |
| 2026-10-01 | WP-5.8 | Use SeaweedFS (Apache-2.0) instead of MinIO as the disposable S3-compatible server in CI and local tests. | MinIO images now require authentication on Docker Hub and quay.io. SeaweedFS's S3 gateway enforces SigV4 with a configured identity, so signatures are really verified. |
| 2026-10-01 | WP-5.8 | Route every asset content read through `app.assets.content`, the single module allowed to resolve `storage_path`. | Assets are either blob-backed (`storage_key`) or file-discovered (voice clones). One module decides how to read, check, materialize or delete either kind on local or S3 storage; `absolute_storage_path_reads` is 0. Local deployments keep returning the same paths in listings. |
| 2026-10-01 | WP-5.8 | Move inline voice-clone samples into the blob store in the job submission policy, and reference generated speech by `audio_url` instead of a base64 `data_url`. | Job rows then hold only a content-addressed key and digest. The web app reads `audio_url` and still accepts `data_url` on older rows; podcast and storyteller already accepted `audio_url`. |
| 2026-10-01 | WP-5.8 | Defer turning directory-scanned voice clones into blob-backed asset records. | Clones are audio plus transcript file pairs read directly by the TTS service on its host. Migrating them is a separate change across voice, audiobook and TTS; the content helpers already handle them as file-managed assets. |
| 2026-10-01 | WP-6.7 | Drain in-process before uvicorn shuts down: the first exit signal enters drain mode (`/ready` 503, new requests 503 + `Connection: close`) and waits for in-flight requests; only then does the server exit. | Uvicorn closes its listener as soon as it gets SIGTERM, so `/ready` could never report not-ready while the replica was still reachable. A second signal falls through to uvicorn (Ctrl+C again forces). |
| 2026-10-01 | WP-6.7 | Add `OMNIX_DRAIN_MIN_SECONDS` (default 0). | An idle replica otherwise drains instantly and closes its listener before the ingress sees it as not-ready. The roadmap's single `OMNIX_DRAIN_SECONDS` cannot express both "at most" and "at least". The rolling test uses 2 s, like a probe interval. |
| 2026-10-01 | WP-6.7 | Add a kernel `platform.probe` job type (bounded, cancellable wait). | Deployment and topology tests need real durable jobs without models or providers; it doubles as an operator canary. Kernel-owned, registered before features. |
| 2026-10-01 | WP-6.7 | The nightly workflow also runs on pull requests that change the drain code, the rolling-upgrade script or the workflow itself. | GitHub dispatches workflows only from the default branch, and `nightly.yml` is not on `main` yet. Path filtering keeps ordinary PRs unaffected. |
| 2026-10-01 | WP-4.1 | Keep sign-in off by default for now (owner decision). | The owner will enable it at a later date. Later Phase 4 work must not assume sign-in is enforced on unset installs. |
| 2026-10-01 | WP-6.5 | Orphan recovery honours a cancel queued for a dead owner instead of restarting the run. | With command delivery fenced to the lease owner, a parent's cancel for an orphaned child is only queued. Recovery used to restart the child's Pi runtime to deliver it, so the child ended `failed` wherever the restart could not run (CI). Recovery now takes the lease, applies the queued cancel and cascades it, without starting a runtime. |
| 2026-10-01 | WP-4.1 | Ship authentication with `OMNIX_AUTH_MODE` unset meaning "not enforced"; any explicit mode enforces. The default flip is the constant `AUTH_ENFORCED_WHEN_UNSET`. | The roadmap makes the no-auth → `local` default change a human gate. Existing installs keep working; operators can opt in now; approval flips one constant (pinned by a test). |
| 2026-10-01 | WP-4.1 | Mount auth endpoints under `/api/auth/*` instead of `/auth/*`. | The Vite development proxy and the production ingress forward only `/api`, `/events`, `/health` and `/ready`. Using `/api/auth` needs no ingress change and keeps the single-origin cookie model. The launcher callback is `/api/auth/local/callback`. |
| 2026-10-01 | WP-4.1 | Keep the `X-Omnix-Client` requirement alongside the new CSRF token. | The roadmap allows CSRF to replace it for cookie-authenticated requests. Keeping both is strictly stronger and changes no client, because the web firewall already sends the header. |
| 2026-10-01 | WP-4.1 | Until WP-4.6, the Pi broker, guard and model-provider routes stay reachable from loopback without a session, through an explicit pinned pattern list. | Those extensions have no user credentials. Run-scoped signed tokens (WP-4.6) replace this. The list is pinned by a test so it can only shrink. Remote clients still get 401. |
| 2026-10-01 | WP-4.1 | The launcher control app is loopback-only (peer address checked) instead of requiring sign-in. | It starts and stops services and opens the browser before a session can exist. The roadmap allows "loopback-only plus the service token"; the peer check enforces loopback even if someone binds it wider. |
| 2026-10-01 | WP-4.1 | OIDC just-in-time provisioning grants only `member` or `viewer`, and never links accounts by email. | Linking by email lets a second identity-provider subject with a matching email take over an account. When an email is already taken, the new user is created without it. |
| 2026-10-01 | WP-1.4 | Retire the legacy RPG test estate and stale retired-contract tests instead of quarantining them; keep a focused RPG roadmap suite. | User direction: legacy RPG tests are retired (archived by the user) and stale tests may be removed and rewritten. Only tests whose contract is retired were removed; current-contract failures were fixed. The quarantine is now empty and guarded by a test. |
| 2026-10-01 | WP-1.5 | Run test-postgres with `--dist loadgroup` and group the shared fixed-ID character tests on one worker. | Those tests share the global `maya` character row; grouping keeps their coverage without serializing the rest of the suite. |
| 2026-10-01 | WP-8.6 | Delete production-unreachable RPG modules now, but keep the five `app.rpg.core` modules the WP-3.3a/b tests import. | The deletion was verified by a whole-package import sweep before/after. The WP-3.3a replay and WP-3.3b golden certify a pipeline production does not use; keeping it preserves that evidence until a production-path golden replaces it (decision for the owner). |
| 2026-10-01 | WP-6.6 | Add `app.caching` as a dependency-free leaf kernel package for `bounded_lru_cache`. | `app.config` needs the cache helper and `app.runtime` imports `app.config`; hosting it in `app.runtime` created a package cycle (AL002). |
| 2026-10-01 | WP-3.8 | Walk FastAPI routes through `fastapi.routing.iter_route_contexts`, falling back to `app.routes` on older FastAPI. | FastAPI 0.141 (locked) includes routers lazily; plain `app.routes` hides them, which silently disabled the blocking-route offload.
