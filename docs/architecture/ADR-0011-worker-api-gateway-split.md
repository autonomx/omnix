# ADR 0011: Worker and API gateway roles

Status: accepted.

One worker/control gateway per workspace owns legacy background workers that must start and stop together through a PostgreSQL advisory lock. Scheduled work has a separate `scheduler` role: worker and scheduler processes may run schedulers, and each `(task, workspace)` has its own PostgreSQL advisory lock. Scheduler replicas compete for task locks in randomized order, so they can divide tasks without sharing the worker's global lock. Each replica retries tasks it does not own, allowing a surviving replica to take over after a task owner exits. A scheduler process does not acquire global background ownership, run recovery directly, or load local TTS.

API replicas serve requests and may dispatch durably owned chat work, but cannot start scheduled tasks, legacy background workers, or recovery. Immutable configuration determines process capabilities; feature registration declares task requirements. Each scheduler task keeps its session advisory lock for its lifecycle. Loss of the scheduler connection stops its tasks before releasing ownership; PostgreSQL releases all task locks if the process crashes. Task callbacks have bounded execution classes, a timeout, no-overlap scheduling, and duration/failure/lag diagnostics. Ingress sends unclassified writes/control to the worker or scheduler owner and allowlisted request paths to APIs. Spawned-process tests certify task splitting without duplicate execution, ownership loss, crash, and handoff.
